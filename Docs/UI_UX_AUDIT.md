## 3. Current journey maps and policy boundaries

1. **Browse → claim:** Home/nav → `/drop` or `/wall` → client search/filter/Nearby over GET `/api/items?status=wall` → `/drop/:slug` or `/wall/:slug` → status/quota/owner check → guest `/account/login?redirect=<item>` → possible onboarding → return to item → claim modal contact/landmark → terms/personal-use → POST request → success overlay → `/account?tab=claiming`/claim detail. Backend rechecks weekly quota, public visibility, status and self-claim. A giver can see a processing item only under their own session; a previously declined claimer can have it hidden. Local browser proof covers guest Wall/detail render plus a separately simulated signed-in pending claim view, not the connected submission transition.
2. **Give:** `/give` photo step supports one item with multiple angles or separately grouped items; AI/cutout can fail while raw photo remains. Details per group → guest login step or current profile check → `/account/login?redirect=/give` → draft restore from local/session storage (photo previews rehydrated) → review → terms/consent → one POST `/api/donations` per separate item group → success reference. Backend can mark new item `imageProcessingStatus=processing` and `publicVisibility=false` until cutout polish completes (`publicWrite.ts:366-467, 547-554`). The success page currently claims immediate publication regardless. The hotfix branch's local emulator proof covered one photo, not bulk or physical devices.
3. **Account/lifecycle:** `/account?tab=giving` → submission ID plus `?item=`/`?claim=` → pending claim Accept or Decline → approved/matched → address confirmation and schedule proposal/response through `ScheduleHandoverPanel` → coordination/chat and permitted courier action → giver marks handed over → claimer confirms received and may upload photo → completed/feedback view. `/account?tab=claiming` → claim ID and status-specific actions, including cancellation. The backend route set has role gates and checks, but delivery confirmation/cancellation policy must be reconciled before any UI label change. `Given`, `being_matched`, `claimed`, `handed_over`, `received` and public `reloved` are distinct meanings.
4. **Deep links:** notifications load request IDs and giver role, then resolve the exact submission plus `?claim=`; claimer routes use `/account/claims/:id`. Gift detail accepts `?claim=`, `?item=`, `?edit=1`; direct protected URLs redirect to login. Track email/reference opens `/track/:reference`. Ops email CTAs land on `/api/*` and use a special redirect handler. The no-session return path and exact multi-item selection have **source support**, but were not re-proven end-to-end in this audit.
