## P1 — Broken but has a workaround, or high-frequency edge case

### Admin claim approve/decline endpoint has no guard against acting on an already-terminal claim
**(code review — not reproduced live; admin login was skipped after the read-only-scope instruction)**

**Flow:** Admin → item-requests → approve/decline
**Where:** `firebase-backend/functions/src/routes/admin.ts:386-429` (`PATCH /admin/item-requests/:id`)
**Expected:** Acting on a claim that's already `approved`, `rejected`, `cancelled`, or already past `handed_over`/`received` should be a clean no-op or a clear error (per test-matrix §8: "does it corrupt state?").
**Actual (from code):** The handler reads the claim, and if `status` in the request body is `"approved"` or `"rejected"`, it unconditionally overwrites `status`, `handoverStage`, and the linked item's `publicStatus` — there is no check of the claim's *current* `status`, `handoverStage`, or `deliveryStatus` before writing. Contrast with the donor-facing equivalent (`matchFlow.ts:390-393`, `donorRouter.post("/item-requests/:id/giver-decision")`), which explicitly checks `if (claim.status !== "pending") return 400`. The admin route has no analogous guard at all.
**Consequence:** An admin re-approving an already-rejected/cancelled claim, or re-approving a claim that's already at `handed_over`/`received`, will silently flip the item back to `publicStatus: "claimed"` and reset `handoverStage` to `"awaiting_handover"`/`"awaiting_delivery_address"` — effectively un-completing a finished handover or reviving a dead claim, with no error to the admin. It also re-sends the claim-decision email and "Yayyy!" notification to the claimer every time it's called, since (unlike the donation-submission status endpoint at `admin.ts:260`, which explicitly gates on `beforeData.status !== status` before emailing) this endpoint has no such gate.
**Traced to:** `firebase-backend/functions/src/routes/admin.ts:386-429`
**Recommendation:** Add the same `status !== "pending"` (or equivalent terminal-state) guard used in `matchFlow.ts`'s `giver-decision` handler, and gate the notification send on an actual status transition the way `admin.ts:260` already does for submissions.

## P2 — Real bug, low frequency or low impact

### Live public listings still show internal "Zone" labels, contradicting the documented fix — "Mumbai Zone 3, Mumbai" observed live
**(live — confirmed via direct GET, reproduced by re-fetching)**

**Flow:** Wall of Kindness → any item whose `publicArea` was cached before the most recent locality fix
**Repro:**
1. `GET https://api-wsyflslyaq-el.a.run.app/api/items?status=wall` (fired automatically by loading `/wall`)
2. Inspect the `locality` field across the 56 returned items.
**Expected:** Per `Docs/RELOVED_PATCH_NOTES.md` (20 Sept: "Locality now shows real neighbourhood names instead of zone numbers, **consistently**"; 21 Sept evening: "Neighbourhood names everywhere, **no more zone numbers**, on the Wall cards and item pages both"), no live item should show a raw zone label.
**Actual:** Item `porter-blue-and-white-bag-muaa4cnr` (id `Fugq6Jhv4DVD4fvHgz35`) is live on the Wall right now with `"locality": "Mumbai Zone 3, Mumbai"`. Its `createdAt` is `2026-09-20T20:39:01Z` — created the same evening as the first "fixed, consistently" claim, and before the 21 Sept evening re-confirmation. Distinct localities observed across all 56 live items: `["Mumbai", "Mumbai Zone 3, Mumbai", "Bandra West, Mumbai", "Juhu, Mumbai", "Andheri West"]` — i.e. the zone-label bug is not hypothetical, it's presently visible to any anonymous visitor on both the Wall grid and this item's own detail page (`/drop/porter-blue-and-white-bag-muaa4cnr`).
**Root cause (traced):** `locality`/`publicArea` is computed **once**, at Give-submission time, via `toPublicArea()` (`firebase-backend/functions/src/routes/publicWrite.ts:285,297,328`) and persisted on the item document. On read, `toPublicItem()` (`firebase-backend/functions/src/types.ts:53-56`) **prefers the stored `publicArea` field over recomputing it**: `doc.publicArea || toPublicArea(fullLocality)`. `toPublicArea()`'s zone-label stripping (`isZoneLabel`, `firebase-backend/functions/src/lib/geo.ts:109-111,137,144`) is correct logic today, but because the value is cached at write time and never recomputed, any item whose `publicArea` was written before a fix to `toPublicArea()` landed keeps showing the old, unfixed value forever — the fix only applies to *new* submissions, not retroactively to existing ones. Given items from just two days ago already carry the bug, a meaningful fraction of the current Wall inventory likely still does.
**Evidence:** Live API response captured above; full item JSON retained in QA run notes.
**Recommendation:** Either (a) stop trusting the cached `publicArea` in `toPublicItem()` and always recompute from the private `locality`/`pickupLocality` source field, or (b) run a one-time backfill script that recomputes and rewrites `publicArea` on all existing item docs using the current `toPublicArea()`.

### Non-transactional read-then-write pattern on claim state-transition endpoints (race window on rapid concurrent requests)
**(code review — not reproduced live; would require two concurrent authenticated write requests, out of scope after the stop instruction)**

**Flow:** Giver accept/decline, handed-over, received, claimer cancel; admin approve/decline
**Where:** All of `matchFlow.ts`'s `/item-requests/:id/giver-decision`, `/handed-over`, `/received`, `/cancel` (`firebase-backend/functions/src/routes/matchFlow.ts:374-778`), plus `admin.ts`'s `/item-requests/:id` PATCH and the submission-status PATCH (`admin.ts:195-286`, `386-429`) — read the document with a plain `.get()`, branch on its current field values in application code, then `.set()`/`.update()`. None of these use `db.runTransaction`.
**Contrast:** The one place this *is* done correctly is claim creation itself (`donor.ts:752-788`, `donorRouter.post("/item-requests")`) — it wraps the availability check and the write in a single `runTransaction`, re-reading `publicStatus` inside the transaction, which is the right pattern and should correctly prevent two accounts from both successfully claiming the same item under concurrent load (Firestore will force one of the two transactions to retry and see the other's committed write). I was not able to load-test this live under the current scope, but the code pattern here is sound.
**Risk on the non-transactional endpoints:** Two requests landing inside the same read-write round-trip (a genuine double-click, or two admin tabs, firing within tens of milliseconds of each other) can both read the pre-transition state and both proceed to write and send notifications — e.g. two "Yayyy! You're matched" emails, or (combined with the P1 above) an admin decline landing concurrently with a giver's own accept and leaving the item/claim in a state that depends on write-order rather than on a validated transition.
**Recommendation:** Wrap these handlers in `runTransaction` the same way the claim-creation endpoint already does, re-checking `status`/`handoverStage` inside the transaction before writing.

## P3 — Polish / inconsistency, not a functional break

### `/account/onboarding` unauthenticated redirect target doesn't match the page you asked for
**(live)**
**Repro:** Navigate to `/account/onboarding` with no session.
**Expected:** Redirect to login with `redirect=%2Faccount%2Fonboarding` (or similar), so a fresh login lands you back on onboarding.
**Actual:** Redirects to `/account/login?redirect=%2Fgive` — after logging in you'd land on the Give flow instead of onboarding. Minor, likely harmless in practice (most people reach onboarding *from* Give), but the redirect target looks hardcoded rather than reflecting the page that was actually requested.

### OTP verify only ever checks the single most-recent code; an older-but-still-valid code is rejected with a generic "Incorrect code"
**(code review, confirmed in `firebase-backend/functions/src/routes/otp.ts:228-264`; a live attempt during this run produced an "Incorrect code" result on a code I believed was current, but I could not cleanly re-verify the exact cause before the scope change stopped further OTP requests — noting both the code-confirmed mechanism and the inconclusive live observation for transparency)**

`otp/verify` fetches all matching, unexpired, unverified OTP docs for the target and sorts by `createdAt` descending, then only ever compares the hash against `[0]` — the single newest record (`otp.ts:243-247`). If a user requests a code twice in quick succession (e.g. a slow first email, so they hit "resend"), and then enters the code from whichever email arrives/is read first, entering the *older* — but still genuinely unexpired and never-used — code will always fail with "Incorrect code," even though nothing about it is actually wrong, it's just been superseded. The copy is misleading: it should distinguish "wrong code" from "a newer code was requested, use the latest one."

## UI/UX Notes

- **Most live Wall items show a bare "Mumbai" rather than a specific neighbourhood**, even though the product intent (per patch notes) is names like "Bandra West." Across the 56 sampled items, only 4 distinct non-generic localities appeared. This is likely because `MUMBAI_AREA_HINTS`/`PINCODE_AREA` in `geo.ts` only recognizes a fixed list of neighbourhoods and pincodes (`firebase-backend/functions/src/lib/geo.ts:26-97`), so any address that doesn't match one of those hints falls through to the generic "Mumbai" fallback. Not a bug per se, but worth knowing the neighbourhood-name feature is only as good as that hint list's coverage — most real donor addresses apparently aren't matching it.
- The **OTP-request "Incorrect code" error is identical wording** whether the code is truly wrong or just superseded by a newer request (see P3 above) — a developer or support person debugging a user's "I can't log in" report would have no way to tell these apart from the error message alone.

## Confirmed Working

All of the following were directly observed live against production during this run, all via read-only navigation or client-side interaction that fired no mutating request (except where noted as occurring before the scope change, which is called out explicitly):

- **Login email validation**: empty submit, malformed address (`not-an-email`), and whitespace-only input are all blocked client-side (native HTML5 email validation) — zero OTP requests fired for any of these.
- **Login phone validation**: the phone-tab input enforces `pattern="[6-9][0-9]{9}"`, `maxLength=10`, `inputMode="numeric"` — typing `12345` leaves the Send Code button disabled; client-side validation matches the backend's `PHONE_REGEX = /^[6-9]\d{9}$/` (`firebase-backend/functions/src/routes/publicWrite.ts:24`).
- **OTP send button is idempotent against rapid multi-click**: three rapid clicks on "Send code" produced exactly one `/api/otp/request` call (button disables immediately).
- **OTP rate limiting works**: after 3 requests for the same email within 10 minutes, the 4th correctly returns `429 {"error":"Too many OTP requests. Try again later."}` (`otp.ts:186-189`) and the UI reflects it rather than hanging.
- **Auth-gated route redirects are clean**: `/account`, `/account/claims/:id` (with a nonexistent ID), `/account/gifts/:id` (with a nonexistent ID), and all of `/admin`, `/admin/item-requests`, `/admin/items`, `/admin/donations`, `/admin/bulk-upload`, `/admin/peer-chats`, `/admin/messages` cleanly redirect to the appropriate login page when unauthenticated — no blank/broken pages, no auth bypass.
- **No privacy leak in public item data**: `GET /api/items/:slug` and `GET /api/items?status=wall` (sampled across all 56 live Wall items) never return flat/wing/building numbers, donor email, donor phone, or requester address in the JSON payload — only sanitized `locality`, a display-only `donorRecognition` alias, and non-sensitive listing metadata. Checked the raw response body, not just rendered UI.
- **Injection/XSS-shaped item slugs are handled safely**: `/drop/<script>alert(1)</script>` and `/drop/' OR '1'='1` are URL-encoded by the router, hit the API as literal strings, and return a generic `404 {"error":"Item not found"}` with no reflected script execution and no stack trace/error leakage.
- **`/track/:reference` with a fake/nonexistent reference** returns a clean `404 {"error":"Submission not found"}` and a generic "Reference not found" UI state — no enumeration signal that distinguishes "wrong format" from "right format, doesn't exist."
- **`/give/success/:reference` is a static, client-only confirmation screen** — it fires no API call at all and doesn't look up or display any real submission data for an arbitrary/fake reference in the URL, so it can't be used to enumerate or leak real donor submissions.
- **Give flow step 1 (photo picker) renders correctly** with the documented single-item/multi-item toggle and photo-privacy notice; not exercised further (photo upload/submit is a write action, out of scope after the stop instruction).
