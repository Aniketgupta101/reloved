# Reloved Control Center — Phase 0 repository audit

**Audited:** 2026-09-29 · **Branch:** `release/admin-dashboard` · **Base:** `5381ecb6eec7d0173cce163acb4430d2423223ee`
**Scope:** Static repository inspection only. No production data, API, emulator, or third-party service was queried. Findings describe code contracts, not the current production state. The untracked master handoff was read as the target brief and is not part of this audit commit.

## Executive findings and recommendation

1. **Reuse the Firebase admin API and existing integration adapters.** `adminRouter.use(requireAdmin)` protects the admin endpoints. The useful foundations are `/overview`, `/orders`, `/orders/:id/notifications`, `/item-requests`, `/support-chats`, `/analytics`, courier routes, notification helpers, and Edesy masking.
2. **Build new server-side read models before expanding the UI.** Current lists read fixed first batches (200–1,500 documents), then filter/sort in memory. No admin list has a cursor, stable ordered pagination, `hasMore`, or a total count. At scale, omitted older/newer records and partial counts can look complete.
3. **Do not treat current analytics funnels as conversion funnels.** `/analytics` takes `max(event count, lifetime document count)` for several funnel steps. The result mixes scopes, counts events rather than unique people, and can make a sequence appear complete when events are absent. The current “accept rate” uses matched/accepted/completed statuses over all claims, including recent pending claims.
4. **Preserve communication behavior while making it visible.** Delivery notification events record email/SMS `sent`, `skipped`, or `failed`, template, masked destination, and time, but only a claim's last 50 are retrievable. There is no global failure feed or manual template-send API. Contact email and chat replies have different audit paths.
5. **Separate genuine product features from legacy shells.** Partner needs and allocations return empty arrays on reads and 501 on writes. They should not be presented as working workflows. Admin bulk upload and partner application review are real capabilities, even though they are not in the current sidebar.

## Current backend read contracts and scalability

| Contract | Current shape/limit | Gap for control center |
|---|---|---|
| `/metrics` | Counts from six first-500 collection snapshots. | No full counts, as-of/completeness flag, or tester policy; `activeAllocations: 0` is hard-coded. |
| `/overview` | First 300 claims, 200 submissions, 500 threads, 500 visible items; server joins item/submission/profile and recent messages. Returns `todayIst`, counts and four lists. | No cursor/timeframe, next 48h, notification status, or delivery completion history. Any cap can undercount. |
| `/submissions`, `/items`, `/item-requests` | First 200/300/200 docs respectively; status filtering and created-date sorting occur **after** fetch. | No server query filter/order with cursor; full Firestore documents serialized to admin browser, including personal fields. |
| `/orders` | First 200 approved claims, filtered by handover/ops state; joins giver identity and notification summaries. | No stable page order/cursor, no date filter or all delivery modes, and N+1 joins. Qualifying records beyond initial 200 are invisible. |
| `/support-chats`, `/peer-chats`, `/contact-messages`, `/waitlist`, `/partner-applications` | Caps of 300/300/200/1,000/200; in-memory sort/filter. | No cursor or authoritative total; chats may involve per-thread reads. |
| `/orders/:id/notifications` | Latest 50 events ordered by creation; missing-index fallback does unordered limit then local sort. | An old event can be omitted before fallback sorting; no global failed-message query or pagination. |
| `/analytics` | 7–60 UTC days of `analyticsDaily`; capped lifetime collection snapshots (1,500 or 500), post-filtered for testers. | No source coverage/completeness metadata, true lifetime totals beyond caps, cohort or unique-user event identity. “Days” is clamped silently. |

No `startAfter`/cursor or page token is present in `routes/admin.ts`. The existing API response arrays do not expose `hasMore` or query snapshot metadata. A truthful v1 should keep aggregate reads on the server, add explicit `asOf`, scope, completeness/error status, and index-backed ordered cursor contracts to every growing list. This is a read-contract recommendation; no backend change was made in Phase 0.

## Source-of-truth data and metric coverage

- **Operational source:** `donationSubmissions` (submission status, identity/contact, submitted/created time, item links), `items` (Wall status/visibility, category, audience, locality, images, submission link), `itemRequests` (claim status, item snapshot, people/addresses, logistics method, handover stage, proposed/agreed slot, ops/courier fields), `donorProfiles` (account/onboarding/identity), `messageThreads` with message subcollections, `contactMessages`, `partnerApplications`, and `waitlistSignups` in `lib/firestore.ts`. `ItemDoc` in `types.ts` types only the core item fields; admin views use local interfaces and `any`/serialized documents for many extended fields.
- **Communication source:** `notificationEvents` stores claim ID, channel, template, audience, masked destination, status (`sent`/`skipped`/`failed`), provider ID/error, and creation time. It primarily covers delivery templates logged through `notificationLog.ts`; it is not an exhaustive audit of every Brevo/MSG91 message in the product. Contact reply status and message-thread data are separate sources.
- **Behavior source:** frontend `track()` sends to PostHog, GA4/gtag, GTM dataLayer, and mirrors selected events to `/api/...` daily counters. `analyticsDaily` stores per-day incremented event totals, not distinct users or sessions. `donation_submitted` and `claim_submitted` are bumped server-side on successful writes; a client event cannot by itself prove the entity completed. `donation_step_viewed` is one aggregate event field, so photo/details/auth step conversion is not currently defensible from this counter alone.
- **Defensible now, within cap caveats:** lifetime documents for signups/onboarded profiles, submitted Drops, current Wall status, claims by recorded status, reloved item status, and time-windowed creations from document timestamps. Fulfillment time medians have sample counts but depend on available timestamps and fallback `updatedAt` logic; label as estimates with sample size.
- **Not defensible from current admin contract:** DAU/WAU/MAU, unique visitors, source attribution, retention/cohorts, user-level drop/claim funnel conversion, exact first-step loss, historical status transitions, exact delivery success rate, or complete notification delivery coverage. Current `claimFunnel.reloved` uses reloved **items**, not the same claim cohort; `giveFunnel` and `claimFunnel` use `max(event total, document total)` at several steps. The UI should show unavailable coverage rather than a derived percentage.
- **Time and tester policy:** daily event keys and analytics range use UTC days; Overview and the morning ops digest use Asia/Kolkata days. Backend analytics excludes known tester identities from document snapshots, while mirrored aggregate counters cannot be reliably de-identified afterward. The Drops page also has its own hard-coded client tester filter. Neither policy proves that historical counters are clean.

## Immediate implementation guardrails from the audit

1. Start with typed admin read models for Overview/attention and cursor-backed lists. Define status, timestamp scope, completeness, and the next action server-side. Keep private addresses and provider credentials behind `requireAdmin`.
2. Make error/partial/stale distinct from empty. Avoid the current pattern of replacing failed reads with `[]` or silently displaying a retained/zero count. Keep the previous successful snapshot visibly dated if refresh fails.
3. Preserve mutation routes and their current lifecycle side effects. In particular, item patch and submission patch are **not** equivalent; notification and claim cancellation happen in the latter. Claims, delivery stage changes, and courier bookings have real third-party effects.
4. Treat notification status as per-event audit, not proof of receipt. A preview reads provider content; it does not send. Any future manual send/resend needs a separate approved server-side action and idempotence rule.
5. Keep partner needs/allocations as unavailable until implemented. Keep bulk upload, partner application review, waitlist, and peer moderation reachable through an intentional secondary surface or documented route migration.

## 2026-09-30 live-read-only audit addendum

The original Phase 0 audit above remains the historical pre-implementation map. The final integration pass subsequently verified the following without changing production:

- The new `/api/admin/control-center/*` endpoints are not deployed, so the local live review adapter uses the existing deployed admin reads and converts them locally.
- Existing production reads returned operational data for `/overview`, `/analytics`, `/submissions`, `/items`, `/item-requests`, `/orders`, `/contact-messages`, `/support-chats` and per-order notification history.
- The supplied configuration supports authenticated Admin API reads. No direct Firebase Admin read-only identity was found or used.
- No server-side PostHog query credential, Search Console property access, Google Analytics Data API access, CrUX key or usable PageSpeed quota credential was found. Live review surfaces those sources as unavailable and does not substitute fixtures.
- Production mutation providers are configured outside the browser, but their credentials are excluded from the live review child process. No vendor status probe, send, call, booking or analytics capture was performed.
- The browser and loopback mutation barriers block all non-read methods before any production dispatch. The automated live tour recorded zero write requests and a deliberate local POST rejection.

Credential names and safe setup requirements are recorded in `ADMIN_CONTROL_CENTER_HANDOFF.md`; no values are recorded anywhere in the branch.
